# 设计讨论 v0 — Telegram 战况消息地图可视化

> 状态: 讨论稿。本文档只记录设计决策与理由,不替代后续的细化文档。
> 原则: 第一性原理(先问系统到底要解决什么)、奥卡姆剃刀(不为尚未出现的规模提前付复杂度)、主流做法优先(有成熟开源组件不自己造)。

## 1. 第一性原理:系统到底要解决什么

核心循环一句话:

> 群里一条"赫尔松方向 10:23 炮击"的非结构化消息 → 变成地图上"赫尔松某点位、炮击、10 分钟前、3 次独立报告"的一个点,并在 15 分钟后自动"变暗",同时永久留档、可回溯。

画地图本身不难,真正的难点是三个转换:

1. **非结构化文本 → 结构化事件**(提取:地名、事件类型、时间);
2. **多源重复报道 → 去重后的一次真实事件**(合并:同一次爆炸被 3 个群报道);
3. **报道时间 → 事件时间**(时间语义:消息发出的时刻 ≠ 事件发生的时刻)。

整个架构都围绕这三个转换设计。

## 2. 总体架构

管道式架构,模块边界清晰,但**单体仓库 + Docker Compose 多容器**起步(不要一上来就拆微服务)。

```
Telegram 群/频道 (1..n)
      │  Telethon 用户客户端长连接(每账号/每群一个监听)
      ▼
┌──────────────┐  原始消息(append-only)   ┌──────────────────┐
│ Ingest 服务   │ ───────────────────────▶│ PostgreSQL        │
│ (Telethon)   │                          │ + PostGIS         │
└──────────────┘                          │ raw_messages      │
      │                                   │ events(详表)      │
      ▼                                   │ snapshots(读模型) │
┌──────────────┐ 已落库消息入提取队列        └────────┬─────────┘
│ Extract 服务  │                                    │
│ (流水线)      │ 1) 词典快匹配(地名表,毫秒级,免费)      │
│              │ 2) 未命中/低置信 → LLM 结构化提取      │
│              │ 3) 新地名 → 解析 agent 流程 → 人工确认  │
└──────┬───────┘ 4) 审核队列(半自动人工闭环)            │
       │ 结构化事件 + 去重合并                         │
       ▼                                             ▼
┌──────────────┐  活跃事件缓存/去重指纹      ┌──────────────┐
│ API 服务      │ ◀────────────────────────│ Redis         │
│ (FastAPI)    │  SSE 增量推送              └──────────────┘
└──────┬───────┘
       │ REST + SSE(GeoJSON)
       ▼
┌──────────────┐  MapLibre GL 实时地图(暗色)
│ Web 前端      │  右侧实时事件流 / 时间轴回放
└──────┬───────┘
       │ Playwright headless 定时截图(复用同一页面,非另写渲染)
       ▼
┌──────────────┐  sendPhoto / webhook
│ 发布 Bot      │ ─────▶ Telegram 频道 / Discord
└──────────────┘
```

要点:服务之间**只通过 Postgres + Redis 交互**(不互相 RPC),这样每个容器都能独立重启、独立扩缩,将来搬 K8s 只是换编排方式。

## 3. 关键决策与理由

### 3.1 消息获取:Telethon 用户客户端,而非 Bot API

| 方案 | 结论 |
|---|---|
| Bot API | ❌ 无法被动监听群:必须被加进群、且读不到加入前历史;大群不会随意加 bot |
| **Telethon / Pyrogram** | ✅ 用自己的账号加入群后收全部消息,war-monitoring 类项目的主流做法 |

- Bot API 只用于**对外发布**地图截图,不用于采集。
- 风险:账号风控(封号 = 数据断流)。对策:尽量用老账号、控制入群频率、不主动发言、session 持久化、后期多账号分组监听(天然支持多账号扩展)。
- 注意 opsec:采集账号与被发布到的频道之间不要有强关联。
- **维护状态风险(调研发现)**:Telethon 仓库已于 2026-02 标记 archived(Pyrogram、GramJS 同样归档)。对策:锁定版本 + 采集器独立容器(坏账号单独重启)+ tdl / tg_history_dumper 做历史冷启动 + t.me/s 公开预览页做降级通道。详见 `docs/RESEARCH-OPENSOURCE.md`。

### 3.2 地名表 gazetteer:整套系统准确率的根基

- **数据源**:OSM / GeoNames 的乌克兰地名生成基础表,后续人工 + LLM 持续补充别名。
- **字段**:`id, name_uk, name_ru, name_en, aliases[](缩写/变体/战时常见写法), lat, lng, admin1(州), admin2(区), hromada, population_tier, source, updated_at`。
- **翻译不是独立环节**:用户说的"翻译"本质是**别名归一化**——把任何语言/写法的地名归一到 canonical place,别名列就是翻译表,不需要单独一张翻译表。
- **最大难点是同名歧义**:乌克兰同名村庄遍布各州。对策:上下文消歧(消息中出现州名/方向词 → 加权)、输出候选集 + 置信度、低置信进人工队列。
- 全表仅几万行,**整体缓存进内存**(Trie/哈希),匹配毫秒级——这就是"读快照表快速提取坐标"的正解:地名表本身就是一张常驻内存的快照。
- **数据源(调研结论)**:GeoNames UA(多语 alternatenames)+ KATOTTH(VIINA 已打包 29,724 聚落 tessellation GeoJSON)+ OSM Geofabrik 乌克兰切片(name:uk/ru/en)三源合一;乌/俄/英/罗马化四列键用 transliterate/cyrtranslit 预生成,消息侧只做规范化查表。同名歧义:层级上下文(州/区名)+ 前线走廊先验(DeepStateMap 多边形)+ 人口/行政等级排序。

### 3.3 表设计:四张核心表,职责分明

采纳用户"多表分工"的直觉,但把每张表的**职责**说清楚:

| 表 | 职责 | 特性 |
|---|---|---|
| `gazetteer` 地名表 | 地名 → 坐标/行政层级/别名 | 慢变维表,几万行,全量内存缓存 |
| `raw_messages` 原始消息表 | 每条 Telegram 消息原样落库 | **append-only 不可变**,是"历史真相";后续所有重提取、重放、分析都靠它 |
| `events` 详表/事件表 | 结构化事件 | `event_id, event_type, place_id(s), occurred_at, reported_at, confidence, source_count, status(auto/confirmed/rejected/edited), payload(JSON 可扩展)`;多行 raw 可合并指向同一 event |
| `snapshots` 快照表 | **读模型**,不是业务真相 | 见下 |

**为什么需要快照表(读写分离)**:
- `raw_messages` / `events` 无限增长,地图页每次刷新不能扫全表。
- 活跃数据(近 1 小时事件)体量很小,快照让它**查询复杂度与历史总量无关**。
- 两个用途:`active_view`(当前活跃事件轻量投影,地图接口直接读)+ `buckets`(地点 × 15 分钟桶聚合计数,支撑热力、次数标注、历史回放)。
- 实现:写入时同步更新 + Redis 缓存。**奥卡姆:先不上 TimescaleDB/ClickHouse**,普通 Postgres 表 + Redis 足够;量真大了再换 continuous aggregate。

### 3.4 提取流水线:词典先行 → LLM 兜底 → 人工闭环

这是用户"AI + 半自动"想法的具体化。**v1 只实现第 1 步(词典 + 规则),LLM 与解析 agent 以接口占位(Extractor 抽象:DictExtractor 先行,LLMExtractor 后续阶段接入),不引入任何 LLM 依赖。**

1. **词典快匹配**:内存地名表直接扫文本,免费、毫秒、可解释,覆盖大部分"地名 + 动词"类消息。
2. **规则 + LLM 结构化提取**:固定提示词("乌克兰战况解析器"skill),输出严格 JSON Schema:`event_type, places[], time_expr, relative_time, weapons[], casualties?`。校验层:输出地名必须能映射回 gazetteer;LLM **禁止自由生成坐标**。
3. **新地名/无法匹配 → 解析 agent 流程**(用户说的"问本地 ai agent"):固定流程 = 收集上下文 → 生成候选(同州同名、拼写变体)→ 输出建议(含坐标、理由)→ **人工确认 → 写回 gazetteer**。确认动作让地名表越用越准(数据飞轮)。
4. **审核队列 UI**:低置信 / 新地名 / 重要事件类型进队列,一键确认/修改/拒绝;拒绝原因与修正别名回流。
5. **时间语义(关键细节)**:严格区分 `reported_at`(消息时间)与 `occurred_at`(事件时间)。"10 分钟前赫尔松炮击" → occurred_at = now − 10min;"昨天夜里" → 解析为日期;无法确定时标记模糊,地图显示"约 X 小时前"。
6. **审核与 2 分钟延迟的取舍**:人工审核不可能在 2 分钟内完成,因此审核**不阻塞发布**——高置信事件即时上地图;低置信/未匹配地名同样即时发布但标注"未确认"(虚线/灰色),人工事后在队列中确认或修正,修正结果通过 SSE 以 update 推送传播到前端。

### 3.5 核验阶梯:规则自动确认 → LLM 判定 → 人工兜底(2026-09-11 更新)

用户的要求很明确:**不要让运营逐条人工确认,地图上给出的信息本身就应当是对的**。因此核验是"自动为先、人工为例外"的阶梯:

| 层级 | 手段 | 现状 | 作用 |
|---|---|---|---|
| L0 确定性 | 多源交叉印证:同地/同类/同时间窗内 ≥2 个独立来源,或 ≥3 条报道 → `auto_confirmed` | ✅ 已实现(`AUTO_CONFIRM_MIN_SOURCES/REPORTS`) | 覆盖绝大多数真实事件;零成本、可解释、可复现 |
| L1 检索增强 | 证据回查:地点是否真在原文出现、是否转发链重复、来源历史准确率 | 部分(合并/转发/撤回已处理) | 压低单源误报 |
| L2 模型判定 | 把"证据原文 + 抽取结果"交给 LLM 做**判定**(不是自由生成),输出 `confirmed/rejected/unsure` + 一句理由 | 接口预留,v2 接入 | 处理 L0 覆盖不到的语义歧义(讽刺、假定语气、旧闻重发) |
| L3 人工 | 详情面板"确认/拒绝",待处理队列 | ✅ 已实现 | 只处理模型也拿不准、且影响大的少数条目 |

约束(避免模型引入不可控错误):

- LLM 只做**判定与实体链接**(把原文地名挂到 gazetteer id),**永远不生成坐标**;挂不上地名就不产生事件。
- 判定结果必须带理由并写入 `events.reason_json`,可在详情面板回看;模型输出解析失败时保持 `unverified`,不猜。
- 提示词版本与模型名随判定结果一起记录,便于回溯"为什么这条被确认"。
- 成本与出境:同一 15 分钟窗内的证据攒批一起判;走 LiteLLM 抽象便于切本地模型;开启前需明确消息原文是否允许出境。

结论:**能,这正是 v2 的既定内容**;而在没有模型 Key 的当前阶段,L0 已经把"每条都要人工确认"降级为"只在自动规则拿不准时人工看一眼"。

### 3.6 去重合并:多群同报 → 一次事件

- 同一次爆炸几分钟内被 3 个群报道 → 应为**一个点**,标注"3 次报告"。
- 朴素版:同 settlement(或距离 < 阈值)+ 时间窗(30 分钟)+ 类型相同 → 合并;source_count 递增。
- 数据量大了再升级 DBSCAN 等空间聚类。**"次数"的语义 = 合并后的独立报告数**。
- **合并是增量式的**:事件先即时发布,后续报告到达时更新计数/位置并推送 update(而非仅 insert)——这是满足 2 分钟延迟的关键,前端必须支持事件更新。
- **三层去重(调研后细化)**:① 强指纹层:规范化文本 + (地名,类型) + 时间桶 + Telegram 转发链 → 直接判重;② 空间层:同一聚落/5km 半径内同类型 + 小时级时间窗 → 合并、累加 report_count、聚合 sources(VIINA one-per-day 模式收紧版);③ 语义层(异步):MinHash/embedding 兜底处理别名与错拼。工具:RapidFuzz + PostGIS ST_ClusterDBSCAN。
- 噪音过滤:否定句("没有炮击")、闲聊、跨群转发重复(消息 id 去重)。

### 3.7 "失效"的语义:显示衰减,不是删除

用户纠结的 15 分钟/1 小时,建议做成**三层显示语义**,底层数据永远保留:

- **0–15 分钟**:直播态——高亮、脉冲动画;
- **15–60 分钟**:近期态——常规颜色;
- **> 1 小时**:移出实时视图默认图层,进历史图层/时间轴回放。

- 不同事件类型可用不同衰减窗口(爆炸 15 分钟,发射/空袭警报 30–60 分钟,后勤/道路事件 1–3 小时),做成**配置项**,上线后用真实数据调。
- **核心原则:过期只影响"看",不影响"存"。** 历史地图 = 同一套数据 + 时间过滤器,免费获得,天然满足"历史信息保留用于后续分析"。

### 3.8 事件类型:可扩展枚举,v1 砍到最小

- **v1 只做单点事件**:`explosion(爆炸), shelling(炮击), drone_hit(无人机袭击), missile_hit(导弹命中)`——与"地点可视化"目标完全对齐,模型最简。
- **v2 再扩展**:点对(发射点 → 落点,missile_launch)、路线(polyline,车队/进展)、区域(防空警报州级高亮)。
- **关键抽象**:`事件 = 类型 + 几何(点/线/面) + 时间 + 属性`。几何做成可扩展字段,后续新类型只加类型定义、不改架构——这就是"可扩展框架"的核心:领域模型稳定,类型注册表开放。

### 3.9 地图与前端

- **MapLibre GL JS**(开源、无 API key、WebGL 性能好)+ React;图层:事件点(聚类 + 热力可选)、乌克兰行政边界、暗色底图。
- **实时推送用 SSE 而非 WebSocket**:HTTP 友好、断线自动重连、实现简单,单向推送场景足够。
- **简单美观**:暗色底图 + 颜色语义编码(类型 × 新鲜度)+ 右侧实时事件流(点击定位)+ 时间轴回放。组件少,信息密度适中。
- 历史查询走同一 API 的按时间过滤(利用 buckets 聚合)。
- **实现细节(调研验证)**:底图用 CARTO Dark Matter(IRONSIGHT 生产验证,与本原型同款);聚类用 supercluster;时间衰减直接用 MapLibre 表达式把 age 映射为透明度/热力权重;SSE 用 sse-starlette。

### 3.10 地图图片转发 Bot

- **奥卡姆要点:不要另写一套静态渲染。** 用 Playwright/Chromium headless 直接截"同一张地图页"(带 `?export` 参数隐藏 UI 元素),定时(如每 15 分钟)或触发式(新事件阈值)截图 → Telegram bot `sendPhoto` / Discord webhook。
- 好处:一份渲染逻辑,网页和图片永远一致;坏处:截图容器占内存,单机可接受。
- 后期想更轻再考虑 maplibre-gl-native 服务端渲染。

### 3.11 部署:先 Compose,K8s 是"以后"

- **Docker Compose 单机起步**:`postgres(+PostGIS) / redis / ingest / extract / api / web / bot`,全部 `restart: always` + healthcheck,数据 volume 持久化。
- **崩溃自启**:Compose restart 策略 + 每服务 healthcheck,必要时 systemd 或 watchtower 兜底。
- **K8s 的迁移时机**:单机扛不住(消息量大、多账号、要高可用)那天。架构上服务间已解耦,迁移只是编排变化,不需要提前付复杂度税。
- **端口(遵守本仓库约束)**:前端 dev 5173,API 8000,Redis 容器内 6379、本机映射 **6398**(避开 Clowder 生产 6399);不用 3003/3004。
- 备份:Postgres 定时 dump + 恢复演练。
- **镜像选型(调研结论)**:postgis/postgis 官方镜像(+pgvector 变体备用);截图任务用 mcr.microsoft.com/playwright 官方容器,Cron/事件驱动、截图失败不影响主链路;采集器独立容器 + session volume + healthcheck。

## 4. 技术栈一句话总结

Python 3.12(Telethon + FastAPI)+ PostgreSQL/PostGIS + Redis + React + MapLibre GL + Playwright + LiteLLM(LLM 抽象层,本地/云端可切换)。全开源、无供应商锁定。

## 5. 奥卡姆剃刀:v1 明确不做的

- ❌ K8s、微服务拆分(单 Compose 多容器即可)
- ❌ TimescaleDB / ClickHouse(快照表 + Redis 够用)
- ❌ 复杂 agent 编排框架(LLM 就一两个固定 prompt 的结构化输出调用;"skill/流程" = 校验 + 重试 + 写回,代码写死)
- ❌ 账号体系 / 多租户(先一个运营者,可选只读访问令牌)
- ❌ 付费卫星底图瓦片(OSM / 免费暗色风格先行)
- ❌ 服务端独立渲染管线(Playwright 截图复用前端)

## 6. 风险清单

| 风险 | 对策 |
|---|---|
| Telegram 账号风控/封号 | 老账号、控制入群频率、多账号冗余、session 持久化 |
| 地名歧义/错误坐标 | 置信度分级 + 人工审核 + 数据飞轮 |
| 公开地图的信息安全与合规 | 决定公开范围;必要时延迟发布、脱敏 |
| 大事件时的消息洪峰 | ingest 只落库不阻塞;去重与限流 |
| LLM 幻觉坐标 | 输出必须锚定 gazetteer,禁止自由生成坐标 |

## 7. 决议记录(2026-09-06)

| 议题 | 决议 | 对设计的影响 |
|---|---|---|
| 公开范围 | **半公开**:有链接即可访问,链接不在公开渠道发布 | 免登录;访问令牌/限流作为可选保护;发布策略谨慎 |
| 实时性 | **≤ 2 分钟**端到端 | 审核不阻塞发布(异步修正);合并必须增量式;SSE 推送 update |
| LLM | **先纯词典起步 → 云端 API 常驻 → 未来本地替换** | Extractor 抽象先行,LLM 走 LiteLLM 便于换 provider;v1 零 LLM 依赖 |
| 监控规模 | **4–10 个群,每天几千条** | 单 Telethon 账号起步(控制入群节奏),多账号留扩展位;该量级 Postgres 无压力 |
| v1 事件范围 | **只做单点事件**;时间关联(发射→落点等)保留接口 | 几何字段抽象为点/线/面;类型注册表开放;v1 只实现点 |
| 底图风格 | **暗色** | MapLibre + 暗色底图;示意原型见 `prototype/map-mockup.html` |

## 10. 半公开访问的安全硬化(防"反向注入")

裸链接方案可行,但"反向注入"要拆成两个真实面分别防守:

1. **内容注入(XSS,页面侧)**:地图内容来自不可信的 Telegram 消息,任何消息文本渲染到页面必须严格转义(纯文本渲染,禁用 innerHTML 注入);CSP 收紧(`script-src 'self'`、无第三方脚本、MapLibre 等资源自托管);页面无用户输入面。
2. **数据投毒(来源侧)**:群里有人故意发假地名/假事件——这是数据问题而非页面问题,页面无写入口,前端无法注入;靠置信度分级、审核队列、来源权重缓解。

配套措施:

- 管理面(审核 UI、Bot 管理、群配置)放**独立路径/端口 + Basic Auth 或 token**,绝不与地图同域同权限;
- 反向代理加每 IP 限流;保留可选 `?token=` 访问令牌(默认不开,按需启用);
- 结论:裸链接 + CSP + 严格转义 + 管理面隔离 + 限流,不需要登录系统(奥卡姆)。

## 11. 开源调研整合(2026-09-06)

完整报告见 `docs/RESEARCH-OPENSOURCE.md`(8 领域 60+ 项目,数据当日实测)。对本设计的增量修正:

- **采集**:Telethon 仍做主路但锁版本;历史冷启动用 tdl / tg_history_dumper;降级通道 t.me/s 预览页。这是头号维护风险。
- **gazetteer 种子数据白捡**:GeoNames UA + VIINA 的 KATOTTH tessellation GeoJSON + Geofabrik OSM。
- **事件类型学**:沿用 VIINA 24 类,裁剪为 Telegram 高频子集,保留 GEO_PRECISION / location_confidence 字段。
- **去重**:VIINA one-per-day 模式收紧到小时级,三层法见 §3.5。
- **交叉验证图层**:DeepStateMap 非官方 API(实测 200,三语 GeoJSON)与 alerts.com.ua 警报 API 做置信度校验与权威源;非官方 API 统一"缓存 + 重试 + 降级"。可选扩展:NASA FIRMS 火点(The Economist war-fire 模型同源)与 adsb.lol 军事航班(GEV / IRONSIGHT 均用)。
- **God's Eye View(参考,不采用主体)**:2026-08 GitHub Trending #1 的 3D 实况地球(纯浏览器,CesiumJS + Google Photorealistic 3D tiles,MIT)。对我们的价值:① 印证"公开信号融合"路线(adsb.lol 军事 ADS-B、NASA FIRMS 等);② 可抄的工程模式——渲染落后一个节拍 + 帧间插值(对应我们时间衰减的平滑过渡)、服务端密钥代理 + SSRF 防护(对应管理面隔离)、供应商请求预算(对应缓存重试降级)、LLM 会话成本硬上限(v2 阶段);③ 其"现在的数据便宜、回放历史才贵"的论断印证我们的快照/桶聚合读模型。不采用其 3D 重客户端、语音 agent、本地 Pinokio 部署——与"轻量 2D + 截图友好 + Docker 半公开"目标冲突。
- **LLM 二期**:instructor + Pydantic;批量攒批分析降成本(telegram-monitor 实践)。
- **差异化确认**:无完整同类开源系统,最接近为 TGeocoder(原型级)与 IRONSIGHT(面板级);本项目"实时提取 + 去重 + 衰减 + 自动发布"的组合真实存在价值。

# Telegram 态势地图：设计收敛与工程交接

> 给下一位实现 agent 的主入口。设计已具备转入工程的基础；目前交付的是前端体验原型和设计资料，真实采集、事件后端、审核和发布尚未实现。
>
> 最新用户要求：高保真配色进一步加深，参考其指定的 `outputs/situation-monitor.html`；完整总结工作与讨论，准备交给其他 agent 开始实现。本次没有代为启动新 agent、创建新任务、连接外部服务或提交代码。

## 1. 交接五件套

### What：现在要做什么

建设一个以乌克兰为首个专题的 Telegram 事件地图工具。将来源消息转为可追溯、可修正、可回看的事件，主要界面是一张暗色地图与一列实时事件；需要时打开详情、图层和运营设置。

当前可交付基线：`prototype/hifi/situation-monitor.html` 深色单文件原型。本文件集中记录范围、状态、取舍、风险和下一步；不是后台已完成的说明。

### Why：为什么这样收敛

用户喜欢 Watchboard、worldmonitor、Bellingcat Ukraine Timemap 的地图与事件组织方式，但认为复杂面板和大量装饰偏离自己的用途。真正的价值不在于多堆数据源，而在于：一条消息如何可靠变成一个地点、一个事件和一个正确时间，并保留证据。

### Tradeoff：采用与放弃

推荐“模块化单体＋受信任内置扩展＋专题配置”。固定地图／列表／详情／时间的联动，把外部来源、提取器、附加图层、发布器分开。放弃首版第三方插件市场、每个组件一个插件、每个插件一个容器，以及为了假定规模提前引入复杂基础设施。

原型用内嵌 SVG 换取稳定离线预览；它不是正式 GIS 引擎。生产地图候选仍是 MapLibre，需接入实际数据后验证标签、缩放、投影与底图策略。

### Open Questions：尚未拍板

运营者需决定共享数据范围、首版发布目的地、真实来源及凭据、部署位置。工程 agent 需验证采集库、瓦片许可／可用性、队列与查询的负载表现。详见第 10 节；这些不阻止先建立脱敏样本驱动的本地链路。

### Next Action：下一位先做什么

先读本文并打开深色原型，再检查仓库归属；用固定样本跑通“原始消息与修订 → 规则候选 → 地名校验 → 事件及证据 → 查询 → 地图”。不要重新开展一轮无边界 UI 发散，也不要直接导入并激活 n8n 文件。工程阶段的具体授权以用户给接手 agent 的请求为准。

## 3. 产品需求与讨论演进

### 用户明确的方向

- 更美观、更简洁清晰、低 AI 感；风格是 Quiet / Dense / Operational / Data-first。
- 地图约 84%，右侧事件栏约 16%；顶部细工具栏；删除多余左上／左下／右下浮动卡片。
- 地点优先，类型其次，时间／报告数再次；减少圆角、胶囊、描边和 Glow。
- 保留爆炸、炮击、无人机、导弹四类色彩语义；时间衰减用透明度与极轻外圈。
- 接近 Watchboard 的产品感觉，但更集中；部分能力可插件化，默认界面不复杂。
- 最新修订：整体颜色更深，采用用户指定 HTML 的近黑冷蓝灰方向。

### 从旧设计延续的工作基线

以下在 `DESIGN.md` 决议记录中已有，但真实来源和部署尚未交付；不要把它们写成实测结果：

- 一个运营者、首个乌克兰专题，约 4–10 个群／频道、每日几千条消息。
- 正常可定位消息，目标从来源发布到地图可见不超过两分钟。
- 首版词典和规则先行、零必需 LLM；后续云端提取，再考虑本地替换。
- 首版四类单点事件；点对、轨迹、区域与复杂关联不提前实现。
- 原始信息留档；衰减只影响显示，支持历史与人工修正。
- 自动地图截图、事件触发、默认至少五分钟间隔；Telegram／Discord 的实际目的地仍需确认。
- 半公开查看方向，运营权限单独保护；“有链接就能看”不能当成访问控制。

### 讨论路径

1. 从高装饰密度的地图概念稿，转为冷静、紧凑的专业阅读界面。
2. 研究相似项目；用户重点认同 Bellingcat Ukraine Timemap、worldmonitor 与 Watchboard。
3. 从“能不能插件化”收敛为外部能力可替换，而非把地图、时间线和列表拆成彼此独立插件。
4. 阅读用户提供的 n8n 导出，明确它位于数据库之后，不能替代采集和事件事实库。
5. 完成 11 条示例事件的离线交互原型；本轮只加深配色、归档交接资料，没有开始生产实现。

### 实现时保持

- 在 1600px 宽屏，原型地图 1344px、侧栏 256px。窄屏允许侧栏保持可读宽度或折叠，不机械坚持比例。
- 默认没有大型浮动说明卡；详情和图层面板仅在操作后出现。来源配置属于运营入口，不扩张默认监控画面。
- 主事件点尺寸稳定，类型用颜色区分，最近事件仅轻外圈。没有持续脉冲、霓虹光晕或装饰性渐变。
- 当前原型：0–15 分钟透明度 1，15–60 分钟 0.78，超过 60 分钟 0.44；标签设可读下限。生产可配置，但不在普通页面讲解实现公式。
- 原型默认近两小时，可选 15／60／120／180 分钟。旧稿“超过一小时移出默认实时层”不是当前原型默认值；正式默认窗口仍可在真实样本测试后确认。
- 城市与事件标签尽量避让；生产实现应使用地图引擎碰撞处理，不能照搬 11 个示例点的手动偏移表到任意事件。
- 国界不等于控制线；不要自行补画前线或战区。城市级坐标不能暗示精确落点。
- 原型固定演示时钟及演示标识必须保留，接真实数据前不得改成虚假 LIVE 状态。

## 5. 工程边界：核心、扩展、配置

推荐路线是自己的轻量核心；直接裁剪 Watchboard 仍是可选路线，但此前没有接入验证来证明更省工。当前交接不要求先 fork 任一外部项目。

| 边界 | 应负责什么 | 不应负责什么 |
| --- | --- | --- |
| 核心 | 原始材料、修订、地名、事件、证据关系、合并／拆分、人工修正、统一查询、任务记录 | 让任意外部插件直接改写已确认事实 |
| 前端核心 | 地图、列表、详情、搜索、类别、时间和选择状态联动 | 各组件自行计算不同的“现在”与事件集合 |
| 来源适配器 | 带稳定外部身份、来源时间、接收时间、编辑／转发信息的原始输入 | 绕过核心直接打地图点 |
| 提取器 | 规则或模型产生候选，附依据与版本 | 自由生成坐标，覆盖人工修正 |
| 附加图层 | 声明内容、时间覆盖、更新时间和图例 | 没有历史数据却把最新图层塞进历史地图 |
| 发布器 | 接收冻结的截图／发布任务，返回结果与外部消息标识 | 跟随某个浏览用户的临时视图发送 |
| 专题配置 | 地区、默认范围、类型与颜色、衰减、来源实例引用 | 包含账号密钥，或宣称换地区零开发 |

“插件”在第一版是随应用发布的受信任内置模块。每个模块可登记 ID、类型、接口版本、配置结构、依赖、健康状态。来源实例与适配器代码分开，一个 Telegram 适配器对应多个群实例。

停用来源、停用提取器、暂停发布和隐藏图层是四种不同动作。隐藏图层不影响采集；停用来源不删历史；仅有提取器停用时应明确积压；恢复从持久检查点继续。

### 建议运行拓扑，尚非最终技术签字

延续候选：Python／FastAPI、PostgreSQL／PostGIS、React／TypeScript／MapLibre、SSE、复用前端的 Playwright 截图。具体版本由工程 agent 查询官方资料、验证后锁定。

按运行特性分组为应用服务、后台工作进程、截图／发布进程与数据库；截图浏览器独立，采集是否进一步隔离由稳定性验证决定。先单机部署，不提前做 K8s。Redis、专用快照表和高级聚类不是首版的前置要求，带索引的查询与持久任务先测量再决定。

不引入 Redis 并不意味着没有队列工作：事务入队、领取租约、重试上限、超时回收、失败状态和持久变更记录仍要实现。数据库通知如采用，只作唤醒，不当成唯一可靠事件记录。

## 6. 数据语义：先守住这几个不变量

```text
消息来源 → 原始消息及修订 → 提取候选 → 核心校验／保守合并／人工修正
                                              ↓
                                  统一事件查询与版本
                                    ↙          ↘
                            地图／列表／历史   冻结发布视图 → 截图 → 渠道
```

### 核心对象建议

| 对象 | 最少保留的信息 |
| --- | --- |
| 来源实例 | 稳定 ID、适配器、配置引用、启停状态、最近成功时间、检查点、缺口 |
| 原始消息／修订 | 来源 ID、外部消息 ID、修订身份、原文、发布时间、接收时间、编辑／转发信息、可用原始链接 |
| 地名目录 | canonical ID、多语言名称／别名、坐标、行政层级、精度、数据来源、版本 |
| 候选与处理结果 | 消息修订、提取器／规则版本、类别、地名候选、时间依据、accepted／ignored／needs_review／failed 结果 |
| 事件及修正 | 稳定事件 ID、类型、几何／精度、发生时间及不确定性、核验状态、版本、修正理由与操作者 |
| 证据关联 | 多对多消息修订—事件关系；转发或后续报告关系；提取与合并依据 |
| 任务／发布记录 | 稳定任务 ID、状态、租约、尝试次数、错误、冻结查询／版本、产物、外部发送结果 |

这不是最终数据库 schema，不要求一对象一表；约束不能因为简化表数而消失。

### 必须明确的规则

1. 消息先持久化，再推进检查点和下游处理。编辑另存修订，不覆盖原始证据；重放不重复创建相同消息。
2. 一条消息可描述多个事件，多条消息可支持一个事件。重提取保留版本，不能静默覆盖人工确认。
3. 地点置信度与事件核验状态分开。无可靠位置进入待定位，不上图；已定位但未核验是另一种状态。
4. 地名别名归一是空间解析，不等于一般全文翻译。同名地点给候选与依据，不能一律取最大城市。
5. `reported_at`、`received_at`、`occurred_at` 分开。“十分钟前”锚定消息发布时间，不锚定重处理时刻；模糊时间保留范围／精度／推断标识。
6. 消息身份去重、转发识别、事件合并分层。单靠城市＋类型＋时间窗不能证明两次袭击是同一件事；阈值需样本校准，合并可撤回或拆分。
7. `report_count` 是关联报告数，不是独立证实数；频道数和已知来源关系另存。不能因为有三个群就显示“三个独立来源证实”。
8. 淡出不删数据。默认历史采用最新修正后的过去事件，标注包含后续修正；精确还原当时认知不是同一功能。
9. 历史查询和衰减基于统一 cursor；晚到消息不伪装成刚发生；实时采集不中断历史浏览。
10. 发布任务冻结专题、范围、类别、时间与所用事件版本。自动发布视图与浏览会话隔离，补采旧数据不触发虚假新警报。
11. 截图与发送不是同一事务。发送成功但确认丢失时进入“结果待确认”；记录并人工处理，不宣称跨服务严格 exactly-once，也不无限重发。
12. 正式 UI 区分无新事件、断流、积压、未配置和错误，健康状态必须来自真实运行记录。

## 7. n8n 导出：看过什么，能借什么

用户文件：

`/Users/terry/Library/Containers/com.tencent.xinWeChat/Data/Documents/xwechat_files/wxid_ei14t5uz1bgm22_425c/msg/file/2026-08/TG_Message_processor_from_databse.json`

这是本地 n8n 工作流导出，而不是已审计的完整开源仓库。导出字段 `active: true` 仅是保存的配置，不证明本机或远端正在运行。本次只解析文件，不执行节点、不导入、不连接其中服务，也未把原文件复制到交接目录。

静态可见链路：定时触发 → Supabase `tg_message` 读取 `processed=false`、最多 100 条 → 聚合正文、时间、消息 ID 与链接 → 模型筛选／中文输出 → 非忽略结果发 Telegram → PATCH 标记处理完成。五次模型路径是错误回退，不是五模型交叉核实；节点名含 Ollama 也不足以确认实际部署了本地模型。

| 可以借鉴 | 接入前必须补齐 |
| --- | --- |
| 批量处理、保留原文及链接、失败回退 | 每条输入的明确处理结果与错误记录，不仅一个 processed 布尔值 |
| 发布流程可作为外围自动化 | ignored 分支没有连接到完成回写，会有重复处理风险 |
| 模型服务可替换的直觉 | 聚合节点产生 `ids_to_update`，后续回写没有可验证地消费这批 ID |
| 数据库与消息输出分开 | PATCH 地址是占位，无法核验行选择器；不能将其直接填表地址后运行 |
| 保留原始消息时间 | 发送成功后回写失败的重复发送窗口；并发领取／租约控制未见实现 |
| 文本整理适合独立模块 | 没有结构化地理事件、地名校验、证据级去重、长期修订体系 |

另需验证长消息分段、启用 HTML 解析时的转义、模型输出结构校验、重试预算和不可信消息中的提示注入。凭据／端点包含占位，不能声称发现有效密钥泄露；接手者仍应避免将未来真实凭据写入仓库。

建议位置：可选翻译／摘要或通知编排模块，不作为唯一采集器、核心事实库或必需前置服务。第一版纯规则链路不依赖 n8n 或模型服务可用。

## 9. 实施顺序与验收

### 第 0 步：接球核验和样本

确认仓库根与现有文件归属，读原型及本文；列明采用的工作假设。建立含正常报告、否定、转发、多事件、同名地点、模糊时间、编辑和撤回的脱敏样本。公开地图准入与发布目标未确认前，只做本地 fixture 流程。

### 第 1 步：固定样本端到端

验收：重放幂等；地图与列表同一查询；已知坐标且未核验可区分；未知地点不上图；报告计数正确；人工修改不被规则重跑覆盖。需要运营修正的最小界面，而不是只有后台字段。

### 第 2 步：真实采集与恢复

验收：正常消息测量两分钟目标；同时记录完整来源延迟、接收、处理和可见时刻，断流／人工等待／补采单独展示但不隐藏失败。重启后材料不丢、不重复计数，无法恢复的时间缺口明确可见。

### 第 3 步：历史、审核与输出闭环

验收：回看不混入未来事件；未知历史的外部图层不展示；补采不乱发；浏览历史不改变自动输出；截图失败不拖垮采集；失败任务可查可处理；备份实际恢复成功。

### 9.6 未核实事件的成因与已修缺陷(2026-09-11)

用 DSH 插件拉全量未核实事件做证据级复核后,结论分两层:

**结构性原因(占绝大多数)**:1286 条未核实事件的独立来源数**全部等于 1**。目前只有两个真实频道,而交叉印证要求"同 place_id + 同类型 + 时间窗",两个频道报的往往是同一波攻击的不同城镇/不同粒度(实测:不同来源、同类型、≤60min、≤60km 的成对事件有 86 组),因此印证不上。这属于"来源不够"而非"规则不灵"。

**已落地的补救:波次级印证(wave corroboration)**。规则:两个**不同来源**在时间窗(`WAVE_WINDOW_MIN`,默认 60 分钟)内、半径 `WAVE_RADIUS_KM`(默认 50 km)内报了**同类型**事件 → 双方都标记 `auto_confirmed`,并在修订记录里写明对端事件 id 与实测距离;只影响核验状态,**不合并点位**(两个城镇仍是地图上两个点)。环境变量 `WAVE_CORROBORATION=0` 可关闭。
- 实跑:`POST /api/v1/admin/reverify` 在真实历史上推进 105 条(随后随实时采集累计到 144 条 wave 印证),抽查确认全部来自不同来源、距离 15–40 km、同类型,同来源误判 0 条;auto_confirmed 由 124 → 268,未核实 1358 → 1214。
- 仍建议接入 1–2 个官方警报频道:真正独立的来源比放宽规则更可靠。

**已修缺陷(会生成错误"多源印证")**:Telegram 消息被编辑后会产生 revision 2/3 的独立原始记录,旧逻辑把每个修订都算一条报道 —— 300 条证据行重复计数、217 个事件报道数虚高、**53 个事件仅凭"同一条消息被编辑两次"就凑到 ≥3 报而被自动确认**。
- 修复:`corroboration_stats` 与合并逻辑改为按"消息族(来源 + external_id)"去重,新修订取代旧修订的证据行而不是新增;
- 历史数据:`.venv/bin/python scripts/repair_report_counts.py [--apply]` 重算报道数、删除重复证据行、把不达标的 auto_confirmed 降回 unverified 并写入修订记录。实跑结果:证据行 2230 → 1930、auto_confirmed 173 → 120(120 条是真正多源或 ≥3 条独立报道)。
